# 🛡️ 비기능 요구 서술

| 영역 | 내용 | ID |
|---|---|---|
| **재실행 안전성** | 같은 `targetDate`로 여러 번 실행해도 확정된 정산 결과가 중복 생성되지 않는다. 배치의 멱등성이 결제 API의 `Idempotency-Key`에 대응하는 장치다 | `NFR-01` |
| **추적성** | 확정된 정산 항목은 수정·삭제하지 않는다. 금액이 바뀌어야 하면 새 배치로 처리한다. 원장의 `ledger_entries`가 append-only인 것과 같은 이유다 | `NFR-02` |
| **외부 호출 타임아웃** | 연결 3초 / 응답 5초 (`service-contracts.md` §2) | `NFR-03` |
| **재시도** | 5xx·타임아웃만 최대 2회 지수 백오프. **4xx는 재시도하지 않는다** — 요청 자체가 틀린 것이므로 재시도해도 같은 결과다 | `NFR-04` |
| **금액 정밀도** | 내부 `BigDecimal`, 원화 정수. JSON에서는 **문자열**로 주고받아 부동소수점 손실을 막는다 | `NFR-05` |
| **로깅** | 배치 실행 단위로 `targetDate`·처리 건수·상태 전이·대사 결과를 남긴다. 에러 응답의 `message`는 로그에만 쓰고 분기 조건으로 삼지 않는다 (분기는 `code`로) | `NFR-06` |
| **동시성** | 가상 스레드(`spring.threads.virtual.enabled=true`)를 적용한다. 외부 서버 동기 호출로 I/O 대기가 많은 구조이므로 근거가 성립한다 | `NFR-07` |
| **DB 커넥션** | 🚧 HikariCP 풀 상한 미정. 서버 3개 × 기본 10 = 최대 30 커넥션이 Supabase 인스턴스 하나로 몰린다. 배치는 청크 처리 중 커넥션을 오래 점유하므로 정산 서버가 특히 영향을 받는다 | `NFR-08` |
| **성능** | 🚧 목표 수치 미정. 3주 프로젝트에서 데모 규모(수백~수천 건)를 넘는 성능 목표를 세우지 않는다 | `NFR-09` |
