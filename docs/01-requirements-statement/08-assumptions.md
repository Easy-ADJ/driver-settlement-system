# 🔗 가정 및 의존

| # | 가정 / 의존 | 성립하지 않으면 |
|---|---|---|
| A1 | 결제 서버가 `GET /api/payments?date=`로 전일 결제 내역을 제공한다 | 배치 Reader를 구현할 수 없다 |
| A2 | 결제 내역 응답에 `tripId`, `driverId`, `amount`, `status`가 포함된다 | 기사별 집계와 운행 ID 추적이 불가능하다 — **`driverId`가 특히 중요하다** |
| A3 | 원장 서버가 기사별 계정 잔액을 조회할 수 있게 해준다 (`ownerType=DRIVER`, `ownerId=driverId`) | 대사 검증을 구현할 수 없다 |
| A4 | 결제 취소는 원장에 상쇄 분개로 반영되며, 취소된 결제는 결제 API 응답에서 식별 가능하다 | 취소분을 제외한 집계가 불가능하다 |
| A5 | 결제·원장 API가 확정되기 전에는 mock/stub으로 개발한다 | 정산 구현이 다른 두 서버 완료까지 대기하게 된다 |
| A6 | 배치 실행 시점에 전일 결제가 모두 확정 상태다 (자정 이후 늦게 도착하는 결제가 없다) | 누락된 결제가 그날 정산에서 빠진다 |

> **A1~A4는 정산 서버가 혼자 결정할 수 없다.** 결제·원장 API 스펙이 확정되는 시점이 정산 구현의 실질적 시작점이다. 원장 API는 결제·정산 **둘 다** 의존하므로 가장 먼저 고정되는 편이 전체 일정에 유리하다.
>
> **A6은 이 문서가 짚어두는 위험이다.** 기획서에 언급이 없다. 데모 규모에서는 문제가 되지 않지만, "왜 이 운행이 정산에 없나"라는 문의가 여기서 나올 수 있다.

A1~A4를 담당자에게 확인하는 질문 목록(Q1~Q5)은 [정의서 §5 외부 인터페이스](../02-requirements-specification/04-external-interfaces.md)에 있다.
