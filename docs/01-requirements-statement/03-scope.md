# 🧱 시스템 경계

## 가. In-Scope

- 일 단위 정산 집계 배치 (Spring Batch Job)
- 기사별 지급액 계산 (운임 합계 → 수수료 차감)
- 정산 배치 실행 이력 및 정산 상세 항목의 저장·보존
- 정산 배치 중복 실행 차단 및 실패 재시작
- 원장과의 대사(reconciliation) 검증
- 관리자용 정산 내역 조회 API
- 정산 상태 전이 관리 (`RUNNING` → `CONFIRMED` → `PAID`)

## 나. Out-of-Scope

| 제외 대상 | 이유 |
|---|---|
| 결제 생성·취소·멱등 처리 | 결제 서버(김주엽) 소유 |
| 분개 기록·잔액 계산·이중기입 정합성 검증 | 원장 서버(이치헌) 소유 |
| **실제 송금 실행** (은행 API·PG 지급 연동) | 이 프로젝트 범위 밖. `PAID`는 "지급 완료로 표시함"까지만 의미한다 |
| 기사 앱 / 관리자 콘솔 화면 | 백엔드 API만 제공 |
| 승객 결제 UX, 운행 배차 | 시스템 범위 밖 |
| 정산 이의제기 프로세스 | 기획서 §3.5 확장 기능 — 시간이 남을 경우 |

> **`PAID`의 의미를 좁게 잡은 것은 의도적이다.** 실제 송금이 없으므로 `PAID`는 "이 정산 건을 지급 완료로 간주한다"는 상태 표시일 뿐이다. 발표·데모에서 이를 실제 송금으로 설명하지 않는다.

## 다. 다른 서비스와의 경계 규칙 ⚠️

**정산 서버는 `payments`, `trips`, `ledger_accounts`, `ledger_entries` 테이블을 직접 SELECT / JOIN 하지 않는다.**<br>
반드시 소유 서버의 API를 경유한다 (`service-contracts.md` §0).

DB가 하나이므로 기술적으로는 직접 조인이 가능하고, 컴파일러도 DB도 이를 막지 않는다.<br>
이 경계는 **오직 규칙으로만 존재한다.** 어기면 이렇게 된다.

1. 정산 배치가 `payments`를 직접 조인한다 (당장은 편하고 빠르다)
2. 결제 담당자가 `payments.status`에 값 하나를 추가한다
3. 정산 배치가 조용히 틀린 금액을 뱉는다 — **컴파일 에러도, DB 에러도 나지 않는다**
4. 정산이 결제에 의존한다는 사실이 문서 어디에도 없어 원인 추적이 오래 걸린다

지급액 계산이 잘못되는 것보다 **잘못된 것을 모르는 상태**가 이 프로젝트가 막으려는 대상이므로, 이 규칙은 편의보다 우선한다.<br>
부득이한 예외가 필요하면 `service-contracts.md` §0의 예외 기록 절차를 따른다.
