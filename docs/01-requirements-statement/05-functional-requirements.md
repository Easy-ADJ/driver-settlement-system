# ⚙️ 기능 요구 서술

정의서의 ID를 괄호로 병기한다. 항목별 수락 기준은 [요구사항 정의서](../02-requirements-specification/01-functional-requirements.md)에 있다.

## 가. 정산 집계 배치 (`FR-B-*`)

매일, 전일 완료된 결제 건을 기사별로 묶어 지급액을 계산하고 저장한다. Spring Batch의 Chunk 지향 처리를 사용한다.

- **읽기**: 전일 결제 내역을 **결제 서버 API로** 조회한다 (`FR-B-01`, `FR-B-02`). 대량 건수를 어떻게 나눠 읽을지는 🚧 미확정이다.
- **계산**: 기사별로 운임을 합산하고 수수료 20%를 차감해 지급액(운임의 80%)을 산출한다 (`FR-B-03`). 취소·실패 결제는 집계 대상이 아니다.
- **쓰기**: 배치 실행 이력을 `settlement_batches`에, 기사별 상세를 `settlement_items`에 저장한다 (`FR-B-04`).
- **청크 트랜잭션**: 일정 건수(예: 100건)마다 커밋하고, 실패 시 해당 청크만 롤백한다 (`FR-B-05`). 배치 전체를 한 트랜잭션으로 묶지 않는 이유는, 수천 건 중 마지막 한 건 때문에 전부 되돌리는 상황을 피하기 위해서다.
- **중복 실행 차단**: 같은 `targetDate`로 이미 `CONFIRMED`인 배치가 있으면 **Job을 시작하기 전에** 예외로 거부한다 (`FR-B-06`). 시작한 뒤에 발견해 롤백하는 방식이 아니다. 중간까지 쓴 데이터가 남을 여지를 없애기 위해서다.
- **실패 재시작**: 실패한 배치는 처음부터가 아니라 실패 지점부터 재시작한다 (`FR-B-07`).
- **추적 가능한 기록**: `settlement_items`에 포함된 운행 ID 목록과 금액을 남긴다 (`FR-B-08`). [§3 문제](./02-problem.md)에 직접 대응하는 요구사항이므로, 다른 요구사항과 충돌하면 이쪽을 우선한다.

## 나. 대사 (`FR-R-*`)

배치가 항목을 다 쓴 뒤, **원장이 말하는 기사 미지급금 합계**와 **정산이 계산한 항목 합계**가 같은지 대조한다 (`FR-R-01`).

원장 잔액은 원장 서버의 잔액 조회 API로 가져온다 (`FR-R-02`). 정산 서버가 `ledger_entries`를 직접 SUM하지 않는다. 그렇게 하면 잔액 계산 로직이 두 서버에 중복되어 어느 쪽이 맞는지 알 수 없게 된다.

불일치는 **차이 금액을 담은 `log.error`와 조회 API 응답의 `reconciliationStatus`** 로 알린다 (`FR-R-03`). 그리고 **불일치 상태에서는 `CONFIRMED`로 올리지 않는다** (`FR-R-04`) — 틀린 금액이 지급 단계로 넘어가지 않게 막는 것이 목적이다.

## 다. 조회 (`FR-Q-*`)

관리자가 기사별·기간별 정산 내역과 상세 항목을 조회할 수 있다 (`FR-Q-01`). 응답과 에러는 팀 공통 포맷을 따른다 (`FR-Q-02`).

정산 내역서를 CSV/PDF로 만들어 보관할지는 🚧 미확정이다 (`FR-Q-03`).

## 라. 상태 관리 (`FR-S-*`)

정산 배치는 `RUNNING` → `CONFIRMED` → `PAID`로 전이하고, 실패 시 `FAILED`가 된다 (`FR-S-01`).

`CONFIRMED` → `PAID` 전이를 API로 노출할지, 정산 확정 시 원장에 지급 분개를 기록할지는 🚧 미확정이다 (`FR-S-02`, `FR-S-03`).
