# 🛡️ 비기능 요구사항

| ID | 요구사항 | 상세 | 우선 | 출처 | 수락 기준 | 상태 |
|---|---|---|---|---|---|---|
| `NFR-01` | 배치 재실행 멱등성 | 같은 `targetDate`로 여러 번 실행해도 확정된 정산 결과가 중복 생성되지 않는다 | M | `SPEC §4.4`, `ERD §4` | 같은 `targetDate`로 3회 실행 후 `CONFIRMED` 배치가 정확히 1건, 기사별 `settlement_items`도 중복 없음 | 확정 |
| `NFR-02` | 정산 항목 불변성 | 확정된 `settlement_items`를 UPDATE·DELETE하지 않는다. 정정이 필요하면 새 배치로 처리한다 | M | `ERD §4` (원장 append-only와 동일 원칙) | 코드에 확정 항목을 수정하는 경로가 없다 | 확정 |
| `NFR-03` | 외부 호출 타임아웃 | 연결 3초 / 응답 5초 | M | `CTR §2` | 응답을 5초 이상 지연시키는 stub에 대해 타임아웃 예외가 발생한다 | 확정 |
| `NFR-04` | 재시도 정책 | 5xx·타임아웃만 최대 2회 지수 백오프. **4xx는 재시도하지 않는다** | M | `CTR §2` | 400 응답 stub에 대해 호출이 1회만 발생한다 | 확정 |
| `NFR-05` | 금액 정밀도 | 내부 `BigDecimal`, 원화 정수. JSON 직렬화 시 **문자열** | M | `CTR §2` | 응답 JSON의 금액 필드가 `"16000"` 형태(문자열)다 | 확정 |
| `NFR-06` | 로깅 | 배치 단위로 `targetDate`·처리 건수·상태 전이·대사 결과를 남긴다. 에러 응답의 `message`는 로그에만 쓰고 분기 조건으로 삼지 않는다 (분기는 `code`) | S | `CTR §2` | 배치 1회 실행 로그에서 위 4항목을 모두 찾을 수 있다 | 확정 |
| `NFR-07` | 가상 스레드 | `spring.threads.virtual.enabled=true` | S | `ARCH §5` | 설정이 적용되어 있다 | 확정 |
| `NFR-08` | DB 커넥션 풀 상한 | DB 분리로 **다른 서버와의 인스턴스 경합은 사라졌다.** 정산 DB 인스턴스가 감당할 상한만 정하면 된다. 배치는 청크 처리 중 커넥션을 오래 점유한다 | S | `ARCH §1`, `ARCH §5` | 🚧 상한 확정 후 작성 | 🚧 |
| `NFR-09` | 성능 목표 | 3주 프로젝트에서 데모 규모(수백~수천 건)를 넘는 목표를 세우지 않는다 | C | — | 🚧 목표 수치 미정 | 🚧 |
| `NFR-10` | 호스트 자원 공유 고려 | EC2 1대에 컨테이너 3개가 뜬다. 정산 배치가 도는 동안 결제·원장 응답이 느려질 수 있으므로 배치 시각을 트래픽이 적은 시간대로 잡는다 | S | `ARCH §5` | `FR-B-09` 스케줄 시각이 심야로 설정돼 있고 그 근거가 문서에 남아 있다 | 확정 |
