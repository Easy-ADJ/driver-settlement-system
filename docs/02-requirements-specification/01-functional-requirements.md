# ⚙️ 기능 요구사항

표기 규칙(우선순위·상태·출처 약어)은 [§1 표기 규칙](./00-notation.md)을 따른다.

## 가. 정산 배치 (`FR-B-*`)

| ID | 요구사항 | 상세 | 우선 | 출처 | 수락 기준 | 상태 |
|---|---|---|---|---|---|---|
| `FR-B-01` | 일 단위 집계 Job | `targetDate`를 Job 파라미터로 받아, 그 날짜에 완료된 결제를 기사별로 묶어 지급액을 계산하는 Spring Batch Job을 제공한다 | M | `SPEC §3.3`, `SET` | 임의 `targetDate`로 Job을 실행하면 해당 일자의 `settlement_batches` 1건과 기사 수만큼의 `settlement_items`가 생성된다 | 확정 |
| `FR-B-02` | Reader는 결제 API 경유 | 전일 결제 내역을 결제 서버 `GET /api/payments?date=`로 조회한다. `payments`·`trips` 테이블을 직접 SELECT/JOIN하지 않는다 | M | `CTR §0`, `SET` | 정산 서버 소스 전체에 `payments`·`trips`를 참조하는 SQL·엔티티가 존재하지 않는다 (코드 리뷰 + grep으로 확인) | 확정 |
| `FR-B-03` | 기사별 집계 및 수수료 차감 | 기사별 운임 합계를 구하고 수수료 20%를 차감해 지급액(운임의 80%)을 산출한다 | M | `SPEC §3.3`, `SET` | 운임 10,000원 2건이 같은 기사에 속하면 지급액 16,000원이 산출된다 | 확정 (율 20%) |
| `FR-B-04` | 정산 결과 저장 | 배치 실행 이력을 `settlement_batches`에, 기사별 상세를 `settlement_items`에 저장한다 | M | `SPEC §3.3`, `ERD §2` | Job 성공 후 두 테이블에서 결과를 조회할 수 있다 | 확정 |
| `FR-B-05` | 청크 단위 커밋 | 일정 건수(예: 100건)마다 커밋하고, 실패 시 해당 청크만 롤백한다. Job 전체를 하나의 트랜잭션으로 묶지 않는다 | M | `SPEC §4.4`, `SET` | 중간 청크에서 강제로 예외를 던지면, 이전 청크의 결과는 남고 실패 청크만 롤백된다 | 확정 |
| `FR-B-06` | 중복 실행 거부 | 같은 `targetDate`로 이미 `CONFIRMED`인 배치가 있으면 **Job 시작 전에** 예외로 거부한다. 시작 후 롤백이 아니다 | M | `SPEC §3.3`, `SET`, `ERD §4` | 같은 `targetDate`로 두 번 실행하면 2회차는 `SETTLEMENT_ALREADY_CONFIRMED`로 거부되고 새 `settlement_batches` 레코드가 **생성되지 않는다** | 확정 |
| `FR-B-07` | 실패 지점 재시작 | 실패한 Job은 처음부터가 아니라 실패 지점부터 재시작한다 (Spring Batch 메타 테이블 기반) | S | `SPEC §3.3`, `SET` | 중간 실패 후 재실행하면 이미 처리된 청크를 다시 처리하지 않는다 | 확정 |
| `FR-B-08` | 추적 가능한 정산 내역 | `settlement_items`에 포함된 운행 ID 목록과 금액을 남긴다. 기사 문의 시 "어떤 운행이 얼마로 계산됐는지" 답할 수 있어야 한다 | **M** | `SPEC §3.3`, `SET` | 임의의 `settlement_items` 1건에서 포함된 운행 ID 전체를 얻을 수 있고, 그 운행들의 운임 합계 × 0.8이 저장된 지급액과 일치한다 | 확정 |
| `FR-B-09` | 배치 트리거 | 정해진 시각에 Job이 자동 실행된다. Spring `@Scheduled`로 정산 서버 내부에서 트리거한다 (`ARCH §5`) | S | `ARCH §5` | 스케줄 시각이 되면 별도 조작 없이 Job이 실행되고, 실행 로그에 `targetDate`가 남는다 | 확정 |
| `FR-B-10` | 결제 서버 장애 시 재시도 | Reader의 외부 호출 실패에 대한 재시도·부분 실패 처리 | S | `SET` | 🚧 정책 확정 후 작성 | 🚧 U2 |
| `FR-B-11` | Reader 페이지네이션 | 결제 건수가 많을 때 나눠 읽는 방식 | S | `SET` | 🚧 결제 API 스펙과 함께 확정 후 작성 | 🚧 U3 |
| `FR-B-12` | 금액 절사·반올림 규칙 | 운임의 80%가 정수로 나뉘지 않을 때의 처리 규칙 | **M** | — (문서 공백) | 🚧 원장 담당자와 동일 규칙 합의 후 작성 | 🚧 U12 |

> **`FR-B-09`는 `@Scheduled`로 확정됐다** (U1). EC2 1대에 정산 컨테이너가 **하나만** 뜨므로 스케줄러 중복 실행을 걱정할 필요가 없다 — 인스턴스를 늘리면 그때는 `FR-B-06`의 중복 거부가 유일한 방어선이 된다.<br/>
> 대신 **정산 서버가 죽어 있으면 그 시각의 배치는 아예 돌지 않는다.** 놓친 날은 `targetDate`를 지정한 수동 실행으로 메운다.

> **`FR-B-12`는 팀 문서에 없던 공백이다.** 운임 3,333원의 80%는 2,666.4원이다. 정산과 원장이 서로 다른 규칙(절사 vs 반올림)을 쓰면 **계산이 정상인데도 대사(`FR-R-01`)가 1원 단위로 실패한다.** 원장 담당자(이치헌)와 함께 정해야 하므로 `contract` 이슈 대상이다.

## 나. 대사 (`FR-R-*`)

| ID | 요구사항 | 상세 | 우선 | 출처 | 수락 기준 | 상태 |
|---|---|---|---|---|---|---|
| `FR-R-01` | 대사 검증 | 배치 종료 후, 원장상 기사 미지급금 합계와 정산 항목 합계가 일치하는지 자동 검증한다 | M | `SPEC §3.4`, `SET` | 원장 잔액과 정산 합계가 같으면 통과, 임의로 어긋나게 만들면 불일치로 판정된다 | 확정 |
| `FR-R-02` | 원장 잔액은 API 경유 | 잔액은 원장 서버 `GET /api/ledger/accounts/{accountId}/balance`로 가져온다. `ledger_entries`를 직접 SUM하지 않는다 | M | `CTR §0`, `SET` | 정산 서버에 `ledger_entries`·`ledger_accounts`를 참조하는 SQL·엔티티가 없다 | 확정 |
| `FR-R-03` | 불일치 통지 | 대사 불일치를 관리자가 인지할 수 있게 한다 | S | `SPEC §3.4`, `SET` | 🚧 통지 수단 확정 후 작성 | 🚧 U5 |
| `FR-R-04` | 불일치 시 확정 보류 | 대사 실패 시 배치를 `CONFIRMED`로 올릴지 결정 | **M** | `SET`, `CTR §1` | 🚧 확정 후 작성 | 🚧 U6 |

> **`FR-R-04`가 M인 이유**: 이 결정이 "대사 실패한 금액을 지급 대상으로 볼 것인가"를 정한다. 결정 전에는 [`FC-01`](../05-flow-chart/01-fc-01-batch-control-flow.md)·[`SD-03`](../04-sequence-diagram/03-sd-03-reconciliation.md)의 분기 하나를 그릴 수 없다.

## 다. 조회 (`FR-Q-*`)

| ID | 요구사항 | 상세 | 우선 | 출처 | 수락 기준 | 상태 |
|---|---|---|---|---|---|---|
| `FR-Q-01` | 정산 내역 조회 API | `GET /api/settlements?driverId=&date=` — 기사별·기간별 정산 내역과 상세 항목을 반환한다 ([§4 명세](./03-api-specification.md)) | M | `SPEC §3.4`, `SET` | 배치 실행 후 해당 `driverId`·`date`로 조회하면 지급액과 포함된 운행 ID 목록이 반환된다 | 확정 |
| `FR-Q-02` | 공통 에러 포맷 준수 | 에러 응답은 `{ "code", "message", "transactionId" }` 포맷을 따르고, HTTP 상태코드로 종류를 구분한다 | M | `CTR §2` | 존재하지 않는 `driverId`로 조회하면 위 3개 필드를 가진 응답이 온다 | 확정 |
| `FR-Q-03` | 정산 내역서 파일 생성 | CSV/PDF 내역서 생성 및 보관 | C | `SPEC §4.3`, `ARCH §5` | 🚧 보관 위치 확정 후 작성 | 🚧 U9 |
| `FR-Q-04` | 조회 페이지네이션 | 조회 결과가 많을 때의 분할 방식 | S | — | 🚧 팀 공통 페이지네이션 방식과 함께 확정 | 🚧 U3 |

## 라. 상태 관리 (`FR-S-*`)

| ID | 요구사항 | 상세 | 우선 | 출처 | 수락 기준 | 상태 |
|---|---|---|---|---|---|---|
| `FR-S-01` | 상태 전이 관리 | `RUNNING` → `CONFIRMED` → `PAID`, 실패 시 `FAILED`. 정의되지 않은 전이는 거부한다 | M | `SPEC §3.3`, `SET` | `PAID` 상태를 `RUNNING`으로 되돌리려는 시도가 예외로 거부된다 | 확정 |
| `FR-S-02` | `PAID` 전이 방식 | `POST /api/settlements/{batchId}/pay`로 노출한다. 확정은 `/confirm`으로 분리 | S | `SET` | `CONFIRMED`가 아닌 배치에 `/pay`를 부르면 409 `INVALID_STATE_TRANSITION`으로 거부되고, 성공 시 배치와 기사별 `payout_status`가 함께 `PAID`가 된다 | 확정 |
| `FR-S-03` | 정산 확정 시 지급 분개 기록 | `/confirm`이 기사별로 원장에 상쇄 분개를 남긴다. 상쇄 금액은 **운임 합계** | S | `CTR §1`, `SET` | 원장 기록이 재시도 후에도 실패하면 배치가 `CONFIRMED`로 올라가지 않고 `ledger_id`도 남지 않는다 | 확정 |

> **`PAID`는 실제 송금을 뜻하지 않는다.** 송금 연동은 범위 밖이다 ([기술서 §4.2](../01-requirements-statement/03-scope.md)). `PAID`는 "지급 완료로 표시함"까지다.
