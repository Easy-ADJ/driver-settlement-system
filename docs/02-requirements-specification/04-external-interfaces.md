# 🔗 외부 인터페이스 요구사항

정산 서버가 **호출하는** 외부 API다. 스펙 확정 권한은 각 소유자에게 있으므로, 아래는 **정산 서버가 기대하는 바**를 적은 것이다.

| ID | 대상 | 엔드포인트 | 목적 | 기대하는 응답 필드 | 실패 시 | 상태 |
|---|---|---|---|---|---|---|
| `IF-01` | 결제 서버 (김주엽) | `GET /api/payments?date=` | 배치 Reader — 전일 결제 내역 | `paymentId`, `tripId`, **`driverId`**, `amount`, `status`, `requestedAt` | Job 실패 → 재시도 🚧 U2 | 확정(시그니처) / 🚧(필드·페이지네이션) |
| `IF-02` | 원장 서버 (이치헌) | `GET /api/ledger/accounts/{accountId}/balance` | 대사 — 기사 미지급금 잔액 | `accountId`, `balance` | 대사 불가 → 🚧 U6 | 확정(시그니처) / 🚧(계정 조회 방법) |
| `IF-03` | 원장 서버 (이치헌) | `POST /api/ledger/entries` | 정산 확정 시 지급 상쇄 분개 기록 | `ledgerId` | 2회 재시도 후 **배치를 확정하지 않는다** (트랜잭션 롤백) | 확정 |

## 정산 서버가 두 담당자에게 확인해야 할 것

| # | 확인 대상 | 왜 필요한가 | 대상자 |
|---|---|---|---|
| Q1 | 결제 내역 응답에 **`driverId`** 가 포함되는가 | 없으면 기사별 집계가 불가능하다. `tripId`만 오면 `trips`를 직접 읽어야 하는데 그건 `CTR §0` 위반이다 | 김주엽 |
| Q2 | 취소된 결제를 응답에서 어떻게 식별하는가 (`status` 값 목록) | 집계에서 제외할 기준 | 김주엽 |
| Q3 | 기사 계정의 `accountId`를 어떻게 얻는가 | `GET /api/ledger/accounts?ownerType=DRIVER&ownerId={driverId}`로 먼저 조회해야 하는지, `driverId`로 잔액을 바로 조회할 수 있는지 | 이치헌 |
| Q4 | 잔액의 부호 규약 (미지급금이 양수인가 음수인가) | 대사 비교 시 부호를 잘못 잡으면 항상 불일치가 난다 | 이치헌 |
| Q5 | 금액 절사·반올림 규칙 (`FR-B-12` / U12) | 두 서버가 다르면 정상 계산인데도 대사가 실패한다 | 이치헌 |

> **Q1과 Q3은 정산 구현의 선행 조건이다.** `CTR §3` 절차에 따라 **결제·원장 레포에 `contract` 라벨 이슈**로 올리고 정산 담당자를 멘션 요청한다. 정산 레포에 쌓아두면 정작 답할 사람이 보지 않는다.
