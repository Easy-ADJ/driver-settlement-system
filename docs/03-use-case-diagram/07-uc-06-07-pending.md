# 🚧 미확정 유스케이스 (UC-06 · UC-07)

**UC-06은 확정됐다** (U7·U8 닫힘). **UC-07은 여전히 미확정이다** — U9(보관 위치)가 DB 제품 결정에 묶여 있다. 아래에서 UC-07 내용을 확정된 것처럼 인용하지 않는다.

---

## UC-06 ✅ — 확정·지급 완료 처리

| 항목 | 내용 |
|---|---|
| **주 Actor** | 관리자 |
| **보조 Actor** | 원장 서버 (`IF-03`) |
| **목적** | 확정된 정산을 지급 완료로 표시한다 |
| **관련 요구사항** | `FR-S-01`, `FR-S-02`, `FR-S-03` |
| **상태** | ✅ **확정 (U7, U8 닫힘)** — API 두 개로 노출하고, 확정 시 원장에 상쇄 분개를 남긴다 |

**확정된 흐름**

| # | 단계 | 일어나는 일 |
|---|---|---|
| 1 | `POST /api/settlements/{batchId}/confirm` | 기사별로 원장에 **상쇄 분개**를 남기고(`Idempotency-Key: settlement-{batchId}-{driverId}`) `RUNNING` → `CONFIRMED` |
| 2 | `POST /api/settlements/{batchId}/pay` | `CONFIRMED` → `PAID`. 기사별 `payout_status`도 함께 `PAID` |

**왜 하나가 아니라 둘인가.** 대사가 불일치를 내면 자동 확정이 일어나지 않는데, **그 배치를 사람이 확인하고 진행시킬 지점**이 필요하다. `/pay` 하나로 보류까지 풀면 "확정을 거치지 않고 지급된 배치"가 생기고, 나중에 `PAID` 레코드만 봐서는 **검증을 통과한 것인지 사람이 밀어붙인 것인지 구분할 수 없다.** 둘로 나누면 `CONFIRMED` + `MISMATCHED` 조합이 그 증거로 남는다.

> **`PAID`는 실제 송금을 뜻하지 않는다.** 송금 연동은 범위 밖이다 ([기술서 §4.2](../01-requirements-statement/03-scope.md)). 발표·데모에서 이를 실제 지급으로 설명하지 않는다.
>
> ⚠️ **원장 상쇄 분개를 빠뜨리면 다음날 배치가 같은 금액을 또 정산한다.** 그래서 확정과 상쇄를 같은 트랜잭션에 묶었다 — 원장 기록이 재시도 후에도 실패하면 배치는 확정되지 않는다.

관련 다이어그램: [`SD-06`](../04-sequence-diagram/06-sd-06-payout-ledger-entry.md), [`FC-04`](../05-flow-chart/04-fc-04-state-transition.md)

## UC-07 🚧 — 정산 내역서 생성·보관

| 항목 | 내용 |
|---|---|
| **주 Actor** | 시스템 |
| **목적** | 정산 내역을 CSV/PDF로 만들어 감사 목적으로 장기 보관한다 |
| **관련 요구사항** | `FR-Q-03` 🚧 |
| **상태** | 🚧 **미확정 (U9)** — 보관 위치는 **DB 제품 결정에 종속된다** (Aurora면 S3, Supabase면 Supabase Storage). 또는 생성하지 않고 조회 API로 대체 |

> 우선순위 `C`다. `FR-B-08`(항목 단위 추적성)과 `FR-Q-01`(조회 API)만으로 [§3의 핵심 문제](../01-requirements-statement/02-problem.md)는 해결된다. 파일 생성은 그 위에 얹는 편의 기능이다.
